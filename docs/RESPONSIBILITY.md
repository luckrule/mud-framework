# 责任边界

本文件说明框架、消费方（游戏应用）与部署/运维之间的职责分工。契约仍以 `docs/SPEC.md` 与 `docs/INVARIANTS.md` 为准；本文件与契约冲突时以契约为准。装配与部署操作见 `docs/INTEGRATION.md`。

## 总原则

- 框架提供执行骨架与契约：连接、请求顺序、Session 路由、事务边界、崩溃恢复、目标化推送、稳定错误码与日志字段、健康快照。
- 消费方提供业务规则：身份、权限、房间/频道、游戏状态、事件语义、幂等与内容过滤。
- 部署/运维提供运行环境：TLS 终止、进程管理、存储运维、备份与恢复、监控后端。
- 判断标准：需要游戏或运营策略的，留在消费方；只描述机制、且多个消费方共用的，才考虑框架 seam。
- 不为未来预留。只有真实消费方证明现有 seam 不够时，才增加框架能力；新增能力不得引入旧版本兼容分支。

## 易混淆的分工

- **认证与授权**：框架只提供 `access` 检查点与 `authorize` 注入点及其拒绝语义（SPEC §3.7）；凭据校验、用户库、角色权限、登录流程、限速与审计属于消费方。
- **Session 保留**：框架只维护活跃路由与终态屏障；Session 状态保留多久、何时结束、重连体验属于业务（SPEC §2、§3.6）。
- **主动事件的可靠性**：框架只提供 best-effort 的目标化投递，无离线缓冲、无投递确认、无去重（SPEC §3.8、ADR-0008）；事件分类、重要事件落库与拉取接口、`eventId` 去重属于消费方；事件授权与内容过滤不在框架内。
- **TLS**：不属于 core，也不属于传输的通用职责；由反向代理或具体传输实现在部署边界终止（SPEC §5.2）。终止 TLS 不替代认证与授权。
- **热升级**：框架编排两阶段激活、`switchTo` 与写者屏障（ADR-0007）；版本到入口的映射与发布策略属于消费方，灰度、回滚与观察窗口属于运维。
- **数据与迁移**：schema、迁移、种子、业务幂等键与重放安全由消费方负责（SPEC §4.7、§6.4；`INTEGRATION.md` 的 schema 初始化示例）。
- **内存容量**：框架只保证每处队列自身有界；进程内存量级估算 ≈ `maxConnections × maxQueuedEventBytes × 2`，是量级估算而非严格上界。连接数上限与每处队列预算由部署方按容器内存设置。超出部署容量时仍可能 OOM；可用性不在框架保证内。
- **在线态**：框架不向 Extension 发断线回调；心跳、`last_seen`、超时清理属于业务。

## 框架明确不做

用户库、密码、token、Session 保留策略、登录协议；房间、频道、队伍、可见性与事件授权、扇出限流；离线事件缓冲、持久化投递、事件去重服务；TLS 终止、证书管理与反向代理配置；备份调度、保留策略、PITR；指标后端、看板、告警规则、追踪后端；游戏规则、NPC、战斗、聊天模型；混合版本兼容（框架假定 Portal 与 Server 同版本发布）。以上都不在 core 内实现。

## 决策规则

需求落到哪一层，按顺序判断：

1. 需要游戏规则或运营策略 → 消费方。
2. 是环境/实现选择（证书、数据库、监控后端）→ 部署方或对应的传输/存储包，不进 core。
3. 是多个消费方共用的纯机制，且不引入游戏领域模型 → 才考虑框架 seam；必须有真实消费方证据。
4. 不得为旧版本、旧字段或旧装配保留 alias、fallback、双路径。
