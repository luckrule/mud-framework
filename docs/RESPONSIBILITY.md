# 责任边界

本文件说明框架、消费方（游戏应用）与部署/运维之间的职责分工。契约仍以 `docs/SPEC.md` 与 `docs/INVARIANTS.md` 为准；本文件与契约冲突时以契约为准。装配与部署操作见 `docs/INTEGRATION.md`。

## 总原则

- 框架提供执行骨架与契约：连接、请求顺序、Session 路由、事务边界、崩溃恢复、目标化推送、稳定错误码与日志字段、健康快照。
- 消费方提供业务规则：身份、权限、房间/频道、游戏状态、事件语义、幂等与内容过滤。
- 部署/运维提供运行环境：TLS 终止、进程管理、存储运维、备份与恢复、监控后端。
- 判断标准：需要游戏或运营策略的，留在消费方；只描述机制、且多个消费方共用的，才考虑框架 seam。
- 不为未来预留。只有真实消费方证明现有 seam 不够时，才增加框架能力；新增能力不得引入旧版本兼容分支。

## 分工表

| 领域         | 框架                                               | 消费方                                                 | 部署/运维                          |
| ------------ | -------------------------------------------------- | ------------------------------------------------------ | ---------------------------------- |
| 连接与传输   | `Transport` 接口、连接准入上限、输入队列           | 选择/实现传输，决定协议与客户端                        | 网络、反向代理、防火墙             |
| 请求顺序     | 同 Connection 有序、同 Session 屏障、有界队列      | 命令语义与业务并发                                     | 容量规划                           |
| Session      | 路由、绑定/解绑、takeover、屏障、失败不应用        | 谁在何时绑定、Session 保留策略、重连体验               | 无                                 |
| 身份认证     | `access` 检查、public/session 之分                 | 用户库、密码哈希、登录/恢复流程、限速                  | 密钥与凭据管理                     |
| 授权         | `authorize(ctx, method, payload)` 注入点与拒绝语义 | 角色、权限、房间可见性、物品归属                       | 审计与合规策略                     |
| 事务         | 每请求事务、提交/回滚边界、超时/取消               | Handler 内幂等、补偿、业务错误码                       | 存储容量与性能                     |
| 存储接口     | `StorageBackend`、能力声明、降级规则               | 选择后端、声明 Extension 依赖                          | 数据库实例与网络                   |
| schema/迁移  | 无                                                 | 建表、迁移、种子数据、数据校验                         | 迁移窗口与回滚预案                 |
| 备份/恢复    | 存储契约；不在 core 内调度备份                     | 恢复后的业务一致性校验                                 | 备份频率、保留、异机存储、恢复演练 |
| 崩溃恢复     | 发现进程丢失、重启、重放、唯一写者屏障             | 业务幂等键、重放安全                                   | 进程监控、告警、重启策略           |
| 主动事件     | 目标化投递通道、请求内缓冲、提交后发送、eventId    | 事件名、收件人解析、payload、去重、可见性              | 无                                 |
| 事件可靠性   | best-effort，无离线缓冲、无确认/去重               | 瞬时事件 vs 重要事件的分类；重要事件落业务状态并供拉取 | 消息系统（如需）                   |
| 在线态       | 连接生命周期事实；当前不向 Extension 发断线回调    | 心跳、last_seen、超时清理、重连                        | 在线人数监控                       |
| 日志         | 结构化字段、稳定 `code`、不因日志抛错改变控制流    | 业务日志字段、审计内容                                 | 日志采集、留存、检索               |
| 指标/追踪    | 现有日志与 `health()` 快照；不内置指标后端         | 指标端点、看板、告警规则                               | Prometheus/Grafana/OTel 等后端     |
| TLS          | 不终止 TLS；`Transport` 边界                       | 客户端使用 `wss://`，不把明文当安全                    | 证书、续期、TLS 代理、HSTS         |
| 进程装配     | `IpcExecutor` + `runServerProcess` 两端函数        | 写 Portal/Server 入口、spawn 命令与 env                | systemd/容器、停止预算、日志轮转   |
| 版本与热升级 | 两阶段激活、`switchTo`、写者屏障                   | 版本到入口的映射、发布策略                             | 灰度、回滚、观察窗口               |
| 测试/负载    | 框架契约与恢复链路测试                             | 游戏逻辑、业务幂等、真实负载                           | 压测环境与生产容量                 |

## 框架必须提供

- 窄接口：`Transport`、`RequestExecutor`、`StorageBackend`，不把具体实现绑进 core。
- Session 语义：绑定/解绑只在成功请求后应用；takeover 不清屏障；失败/超时/取消不改变路由。
- 执行契约：每请求事务、同 Connection 有序、同 Session 串行、有界队列、超时与取消。
- 生命周期：两阶段激活、崩溃重启与重放、唯一写者屏障、`switchTo`、有界关闭。
- 推送通道：`ctx.emit` / `ctx.emitToSession`，事件先缓冲后发送，失败可观测。
- 可观测契约：稳定 wire 错误码、日志字段名、`health()` 快照。
- 明确非目标：本文件列出的消费方/部署职责，不得在 core 内实现。

## 框架明确不做

- 用户库、密码、token、Session 保留策略、登录协议。
- 房间、频道、队伍、可见性、事件授权与内容过滤。
- 事件授权与扇出限流。框架不限制单发射方对单目标 Connection 的事件灌注量；事件缓冲有界只保证不 OOM，不保证可用性。房间权限、可见性、扇出速率由业务负责。
- 离线事件缓冲、持久化投递、事件去重服务。
- TLS 终止、证书管理、反向代理配置。
- 数据库备份调度、保留策略、PITR。
- 指标后端、看板、告警规则、追踪后端。
- 游戏规则、NPC、战斗、聊天模型。
- 混合版本兼容；框架假定 Portal 与 Server 同版本发布。

## 消费方必须自备

- 认证与授权：凭据校验、不可猜测的 Session/token、角色与权限、限速与审计。
- 在线态：心跳、`last_seen`、超时清理；不能假设框架会通知业务"某连接断了"。
- 数据：schema、迁移、种子、业务幂等键、重放安全。
- 事件：收件人解析、事件分类、重要事件持久化与拉取接口、`eventId` 去重。
- 可观测：指标端点、看板、告警；框架只提供日志与健康快照。
- 部署：TLS、进程管理、备份与恢复演练（与运维共同负责）。

## 决策规则

需求落到哪一层，按顺序判断：

1. 需要游戏规则或运营策略 → 消费方。
2. 是环境/实现选择（证书、数据库、监控后端）→ 部署方或对应的传输/存储包，不进 core。
3. 是多个消费方共用的纯机制，且不引入游戏领域模型 → 才考虑框架 seam；必须有真实消费方证据。
4. 不得为旧版本、旧字段或旧装配保留 alias、fallback、双路径。
