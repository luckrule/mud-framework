# ADR-0002: 双进程分离

## 背景

框架核心承诺之一是业务进程崩溃或升级时玩家连接不断（P4、INV-001、INV-012）。单进程内做优雅重启只能覆盖主动重启：进程崩溃时，传输连接、内存中的 Session 路由与未确认输入同时消失，没有东西能接住它们，重放也无从谈起。

要把"连接活着"与"业务能崩"同时做到，持有连接的执行体必须与执行业务的执行体不是同一个故障域。这决定了连接状态与业务状态的归属必须分离，且两者之间的通信必须是显式协议，而不是共享内存。

拆分同时带来硬约束：INV-002 要求业务进程是存储的唯一写者。若连接层也能写存储，恢复时就有两个无协调的写者，事务边界与请求顺序都无法成立。

## 决定

分为两个进程：

- Portal 进程：持有 Transport 连接、Session 路由、每连接的 Input Queue 与未确认输入缓冲。不执行 Handler，不访问存储。
- Server 进程：持有 Extension、Handler 执行与存储写入权，是存储的唯一写者。

两者通过 IPC 通信，进程由 `Bun.spawn` 拉起。Request 在 Portal 侧分配标识并保持到重放，跨进程投递与重放不换标识（见 SPEC 6.3）。Server 崩溃后 Portal 发现进程不在、重启并重放未确认输入，顺序与原始接收顺序一致。

恢复语义为 at-least-once：重放缓冲的移除条件是确认，不是终态（见 SPEC §2 与 5.4）。

## 后果

获得：Server 崩溃或替换时连接不断；已接收但未确认的输入可重放；升级业务代码不必断开玩家。这是单进程架构拿不到的，也是双进程存在的唯一理由。

代价与必须接受的限制：

- 每个 Request 多一次跨进程投递与序列化，IPC 是热路径上的固定成本；`Bun.spawn` 的 IPC 仅与其他 Bun 进程兼容，跨 Node 需退化为 JSON 序列化，类型与二进制载荷受限。
- 需要实现恢复屏障（Server 就绪前 Portal 不投递）与重放去重所需的元数据，Portal 与 Server 的生命周期必须联合管理，启动与关闭顺序受 SPEC 5.2、5.3 约束。
- 调试从单进程断点变为双进程，请求标识与日志字段是唯一的关联手段。
- 幂等必须由业务负责，框架不提供去重。同一 Request 可能被执行多次，扣钱、发物品、唯一命名这类效果必须由 Extension 用幂等键实现（INV-011）。
- Portal 不得直接访问存储，否则恢复语义失效——崩溃时 Portal 已写入而 Server 未确认的部分无法重放，也无法回滚。

重放不是无限重试：同一 Request 连续失败到上限必须进入终态（SPEC 5.5）。进程分离本身不提供业务状态在重启后的正确性，那属于业务的幂等设计（P4 边界）。
