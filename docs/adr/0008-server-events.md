# ADR-0008: Server 主动事件

## 背景

请求/响应只能回答“这次调用发生了什么”。很多业务需要 Server 主动通知：一个玩家进入房间后，同房间的其他玩家要收到描述；一次状态变化要通知另一个 Session；异步完成后要告诉发起者结果之外的信息。把这些都做成“客户端轮询”或“让客户端多发一次请求”会引入额外的往返与竞态，且无法表达“在提交之后、恰好以这次变更的名义”发出的通知。

候选方案有三类：

- 通用 pub/sub（主题、订阅、退订）与房间/频道抽象。它们把“谁该收到”变成框架的领域模型，而框架不认识房间、队伍或可见性，这是业务概念。加进来会让框架承担无法定义的授权判断。
- 离线事件缓冲与持久化投递。它把事件从“通知”提升为“消息”，要求框架决定保留多久、何时重投、如何幂等，等于引入一套消息系统；这与“连接层不保存业务状态、业务进程可重启”的边界冲突。
- 一个最小的、绑定在请求事务上的事件出口：handler 在请求内声明要发的事件，框架在请求提交后按目标投递，投递失败只记录。

选择第三种。它不发明新模型，只给已有请求补一个“提交后的通知”通道，并明确它不是可靠消息。

## 决定

### API：两个入口，目标在投递时解析

- `ctx.emit(event, payload)`：发给当前请求的 Connection。
- `ctx.emitToSession(sessionId, event, payload)`：发给该 Session 当前的 holder。

`emit` 的地址是请求入口的 Connection，不是 Session：一个请求在入口无 Session 时也可以发事件。`emitToSession` 存的是 Session id，Portal 在真正写出前才用路由表解析当前 holder。收件人因此是“写出时”的 holder，而不是 handler 运行或事件入队时的连接：排队期间 takeover 会把事件改投新 holder，至多重投递一次，二次变化即丢弃；没有 holder 就丢弃，不排队等它上线。事件随重连跟随 Session，但只跟随一次写出前的变化，不是对所有后续 takeover 的保证。同一 Session 的 session 目标事件按发射序串行：后一条等前一条写出或丢弃后才投递，因此 takeover 不改变同一收件 Connection 上这些事件之间的顺序。串行只覆盖 session 目标事件：同一 Connection 上 connection 目标与 session 目标之间不保证发射序，两者只是共享该连接的写出调度器。

事件名与 payload 对框架不透明，框架只校验事件名非空、`emitToSession` 的 Session id 非空。事件名是业务契约的一部分，框架不维护枚举。

### 事务边界：先提交，后发送

handler 调用 `emit`/`emitToSession` 时只写入本请求的缓冲，不触碰 IPC 或网络：

- 请求成功提交后，框架才发送缓冲的事件。顺序固定为“先结果、后事件”，Portal 按 IPC 顺序处理。
- handler 抛错、请求超时、被取消、事务回滚时，缓冲的事件随请求一起丢弃。没有“半个请求的通知”。
- 事件一旦发出就不回滚：Handler 无法得知投递结果，框架也不在事后撤销。投递是 best-effort：可能因目标缺失、连接已关闭、编码或写失败而丢失；请求重放可能让同一事件以相同 `eventId` 再次发送。框架不提供投递确认或去重，需要去重的客户端可用稳定的 `eventId` 自行判断。
- 请求终态后（超时、取消）再调用 `emit`/`emitToSession` 会被拒绝，与事务句柄的失效边界一致。

事件数量按请求有界。超过上限时 `emit` 抛普通错误，handler 可以捕获并决定丢弃哪些；未捕获则整个请求失败，缓冲的事件全部丢弃。这样做而不是静默丢弃，是因为只有 handler 知道哪些事件可以放弃。

### IPC 与线格式

Server → Portal 使用独立消息：

```text
{type:'event', eventId, target, event, payload}
```

`target` 是 `{kind:'connection', connectionId}` 或 `{kind:'session', sessionId}`。`eventId` 为 `${requestId}:${index}`（`index` 从 0 递增）：同一请求、同一发射顺序的重放得到相同 id，客户端可以据此去重，框架不保存去重状态。

客户端下行帧分两类，响应帧保持不变：

- 响应：`{id, ok, ...}`（现有形状）。
- 事件：`{kind:'event', eventId, event, payload}`。

响应帧不加 `kind:'response'`：旧客户端只需要忽略不认识的帧，不需要同时适配两种判别方式；而事件帧必须能和一个响应区分开，所以它有 `kind`。

### 投递语义：best-effort

- Portal 收到事件消息后，`connection` 目标查连接表，`session` 目标在实际写出前重新解析当前 holder。目标不存在、连接已关闭、没有 holder、编码失败或传输写失败时，记一条 warn 并丢弃。不因失败缓冲或重试，不让任何请求失败。
- `session` 目标排队期间发生 takeover 时改投新 holder，至多重投递一次；再次变化即丢弃（`EVENT_DROPPED`）。
- `session` 目标按 Session 串行：同一 Session 的事件按到达顺序逐条处理，后一条在前一条写出或丢弃后才开始投递。串行分两段，只有前一段可取消：**queued**（尚未开始写出）时旧连接被移除或 abort，事件丢弃（`EVENT_DROPPED`，reason 指明写出前连接已关闭）并立即释放串行位，后续事件继续，不会因旧链不再前进而永久阻塞；**writing**（已开始写出）时 abort 不提前释放串行位，必须等实际写结果结算：帧可能已写出，提前释放会让后一条越过前一条。写失败记 `TRANSPORT_SEND_FAILED`（`stage: 'send'`）而不是 `EVENT_DROPPED`。写出本身有界：传输发送受其 `sendTimeoutMs` 约束，底层发送 Promise 不保证 settle 时以发送超时为上界，不用 abort 信号代替。串行只保证顺序，不改变 best-effort 语义：事件仍可能被丢弃。
- 同一 Connection 上事件帧的相对顺序由该连接的写出调度器与传输发送队列保证；同一 Session 的 session 目标事件另由串行队列保证发射序。connection 目标与 session 目标之间不保证发射序，不同 Connection 之间不承诺全局顺序。结果帧与事件帧之间的顺序按文末决策记录的请求工作优先规则。
- 结果发送失败时，Server 跳过该请求的全部事件并记录；请求本身的成功状态不变。
- Portal 开始关闭后不再向事件通道注册/派发；关闭期间及之后到达的事件按 best-effort 丢弃。

事件不是可靠消息：没有离线缓冲、没有事件持久化、没有投递确认、没有去重服务。需要“不能丢、按顺序、跨会话事务”的通知，应当建成业务状态并让客户端读取。

### 安全边界

框架不做事件授权。handler 可以通过 `emitToSession` 向任意 Session 发事件；谁在哪个房间、能否看到某条消息、是否允许跨玩家通知，都是业务规则。框架只提供寻址，不提供可见性模型。同理，事件 payload 不经过框架的内容检查，业务必须自行确保不把不该发给该玩家的数据放进去。

## 后果

获得：一个不需要新模型的事件通道；事件与请求事务的边界明确（提交后才可见，回滚即消失）；寻址与重连解耦（Session 目标在投递时解析）；客户端可用稳定 id 去重。

代价与必须接受的限制：

- 事件可能丢失：目标不在线、连接正在关闭、编码失败、传输写失败都只留下 warn。业务不能把事件当作可靠投递。
- 事件可能重复：重放会以相同 `eventId` 再发一次；客户端去重只是可选优化，不是框架保证。
- 事件的全局顺序不承诺；同一 Connection 上事件帧的相对顺序有保证，同一 Session 的 session 目标事件还按发射序串行。connection 目标与 session 目标之间、跨 Connection 的顺序仍不承诺。
- `eventId` 的稳定性依赖“同一请求的发射顺序稳定”。handler 若按外部时间或随机分支决定发射顺序，重放会产生不同 id；业务需要自行接受这一点。
- 不做通用 pub/sub、房间/频道抽象与离线事件。需要广播时，业务自行维护成员列表并逐个 `emitToSession`，或由客户端读取状态。这条边界是有意的：引入主题模型就必然要把授权与生命周期也搬进框架。

## 决策记录：事件缓冲有界与结果优先调度

本记录修订上文“投递语义”的写出部分；API、事务边界、`eventId` 与 best-effort 语义不变。

### 决定

- 连接层持有的每一处事件缓冲（每 Connection 的事件队列、每 Session 的待投递队列）都有显式上界，按帧数与字节数分别计量。默认 `maxQueuedEvents` 为 1024 帧、`maxQueuedEventBytes` 为 4 MiB；这两个数字的权威常量定义在 `packages/core/src/portal/connection-admission.ts`（与 `DEFAULT_MAX_QUEUED_PER_CONNECTION` 同处）；选项 `maxQueuedEvents` 与 `maxQueuedEventBytes` 声明在 `ConnectionLayerOptions`。此处记录决策值并与其保持同步。上限是每个队列实例的上界，不是每 Connection 汇总的上界。达到任一边界时丢弃新事件，记录 warn（`EVENT_DROPPED`，`reason: 'backlog'`，字段见 SPEC §7.1），不静默丢弃，不改变请求终态。
- 写出仍是单写者：每个 Connection 的写出由其内部调度器串行执行，不同 Connection 之间并发。请求工作指从输入准入到结果写出的整段（读输入 → 准入 gate → 执行 → 写结果），是一个调度单元，不是仅写结果帧；请求执行不得留在原链而只把结果帧交给新队列，否则会出现两个写者。调度改为请求工作优先——有就绪的请求工作时先处理，没有才写事件。结果帧因此可以越过尚未写出的事件帧；事件帧之间仍保持发射序（具体范围见上文“投递语义”）。
- 请求优先不得使事件无限期饥饿：事件的等待被有界数量的请求工作限制。放行间隔是实现常量（当前为每个请求工作后一帧），不构成契约；请求优先只决定两者同时就绪时的顺序，公平规则只承诺有界等待。
- 连接层开始关闭后停止接收新事件；每一处事件缓冲内尚未写出的事件，以及 Session 泵已取出、尚未交给连接队列的在手帧，一并丢弃并只记一条 `EVENT_BACKLOG_DISCARDED` 汇总日志（`reason: 'shutdown'`，字段见 SPEC §7.1），不逐条记 `EVENT_DROPPED`。关闭只排空请求工作，不为事件消耗关闭预算。
- 单个连接断开时（层仍在运行）走另一条路径：尚未开始写出的帧被取消并逐条记 `EVENT_DROPPED`。层关闭与断线两种情形下，已经开始写出的帧都不被抢占，按实际写结果结算，失败记 `TRANSPORT_SEND_FAILED`。

### 理由

- 慢读者可让事件无界增长：事件发射速率 λ 持续大于写出速率 μ 时，积压按 (λ−μ)t 线性增长，进程内存没有上限。传输层的发送超时只约束单帧，不约束积压深度；每 Connection 的事件队列之外，Session 待投递队列在解析出 holder 前同样无界，只给连接队列加界会漏掉这条路径。
- `SendQueue` 的有界保护对事件路径失效：事件写出经连接调度器串行，同一时刻最多一个事件帧在途，传输发送队列的深度恒约为 1，`maxQueuedFrames` / `maxQueuedBytes` 永远达不到。
- 事件与请求共用一条链：FIFO 下大量待写事件排在请求结果之前，一次慢读会推迟整条连接上的所有结果。

### 被否决的方案

- per-request 屏障 + 双链（结果链与事件链各一条，按屏障协调）。复杂度高，且必须重新定义结果帧与事件帧之间的跨链顺序；收益不足以抵消。
- 只补文档不改行为。慢客户端导致的 OOM 仍然会发生。

### 残余边界

- 已经交给传输的那一帧事件无法被后续结果抢占；慢客户端上正在写的事件帧会让下一个结果多等一帧的写出时间。这是单写者的固有代价，不是保证。
- 上限只保证不 OOM，不保证可用性。框架不限制单发射方对单目标 Connection 的事件灌注量；房间权限、可见性与扇出速率由业务负责（`docs/RESPONSIBILITY.md`）。
- 事件通道不按进程代过滤：两阶段激活期间，旧代 Server 仍在途的事件可以继续到达并写出。事件是 best-effort，框架不因切换重放或额外丢弃它们；需要严格代际隔离的场景由业务自行在事件内容里标注。
