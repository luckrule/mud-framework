# ADR-0003: 存储边界

## 背景

不同数据库的并发模型、事务能力与异步真实性差异巨大：SQLite 单连接同步，Postgres/MySQL 连接池且真异步；方言与错误码体系各不相同。把这些差异抽象成“等价的后端”会让框架声称自己提供了并不存在的能力，正是 P3 与 INV-009 禁止的。

若框架内置某个后端，框架的发版就被该驱动升级绑架，零运行时依赖（ADR-0001）也无法成立。INV-016 要求框架包只定义接口与能力声明，不包含任何实现。

## 决定

框架只定义 `StorageBackend` 接口与能力声明类型，不含任何后端实现，也不 import 具体后端包。

- 后端是独立包，独立发版、独立测试；新增后端不改框架核心。
- 能力声明全部字段必填：`transactions`、`concurrency`、`snapshotRead`、`uniqueConstraint`、`maxTransactionDurationMs`。无法提供的值显式声明为最弱一档，不省略。
- 框架按声明降级，并把降级事实记为启动时一次的告警日志；Extension 的依赖按最低要求声明，不满足时 fail fast（SPEC 4.3）。
- 实际请求超时取 `min(框架配置, 后端声明 maxTransactionDurationMs)`。
- `concurrency: 'single'` 的后端必须在内部串行化事务，框架不感知该排队（INV-017）。

## 后果

获得：框架不随任何驱动升级发版；消费方按需安装后端；测试零外部依赖；能力差异是显式契约，而不是运行时嗅探。

代价与必须接受的限制：

- 接口一改，所有后端都要同步改，属破坏性变更。这是刻意选择的成本：接口窄且稳定，优于把后端塞进核心。
- 能力声明的准确性由后端自己实现和测试，框架无法验证。虚报声明（如把同步单连接报成 `pooled`）会让降级路径失效，且故障只在崩溃或并发时暴露。
- 框架无法保证任意后端语义等价。声明之外的行为属于未定义，消费方换后端必须重新评估 Extension 的依赖。
- `transactions: 'none'` 的后端没有回滚，失败时已写入的部分保留，补偿或幂等由 Extension 承担。
