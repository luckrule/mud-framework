# ADR-0005: 移除传输能力协商

## 背景

原契约要求传输实现导出 `TransportCapabilities`：二进制帧、分片、单条消息上限、背压、有序交付与心跳归属，字段全部必填；框架按声明降级，`Transport` 接口因此带有 `capabilities()`。

这套契约没有成为可执行行为：框架代码没有调用 `Transport.capabilities()`，降级路径未实现；真实传输声明全强，测试替身声明最弱，框架对两者不做区分。声明既不能改变框架行为，也没有消费者。

## 决定

移除传输能力协商：

- 删除 `TransportCapabilities` 及其公共导出。
- 从 `Transport` 接口删除 `capabilities()`；接口只保留 `start`、`stop` 与传输的职责边界（接受连接、交付入站数据、写出发站数据、关闭，见 SPEC 5.2）。
- 传输不需要能力协商。框架的顺序、队列上限、重放与 Session 路由都在连接层实现（SPEC 5.2），不按传输能力分叉。能力声明只有在框架为每种声明准备好替代实现时才是契约；否则它只是让传输作者以为声明弱能力会触发降级，而框架并不会。
- 存储能力声明保留：`StorageCapabilities` 驱动事务超时、降级告警与 Extension 的 `requires` 校验，后端能力有真实差异（SPEC 4.2、4.3）。

## 后果

- 接口收窄是破坏性变更：所有传输实现 MUST 同步修改（SPEC 8.2）。
- 传输作者不再声明能力字段，只需实现 `Transport` 的职责。无法承担接口职责的传输不受支持；不要为它设计框架未实现的降级模式。
- 存储能力与传输能力不是同一类契约：前者的差异会改变事务与启动结果，后者的差异没有可观察的框架行为。
